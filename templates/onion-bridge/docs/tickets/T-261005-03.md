# T-261005-03 — Add authentication to web control API and UI

## Goal
Protect the Onion web control plane (`onion web` API + dashboard) so unauthenticated callers cannot list projects, start/stop bridges, or change settings when the control port is reachable off-machine.

## Do
- Add control-plane auth with modes aligned to MCP where practical: at least `token` (shared secret) and a path to reuse/configure `oauth` later; default remains safe for pure localhost use (explicit local-dev compatibility mode allowed).
- Require auth on `/api/*` mutating and sensitive read routes (projects, start/stop, settings, browse-folder, flags). Keep a minimal unauthenticated health check if useful for probes.
- Reject missing/invalid credentials with clear `401` responses; never log secrets or full `Authorization` headers.
- Teach the web UI to send credentials (token header and/or login/session UX minimal enough to use from a phone browser off-home).
- Persist non-secret auth mode settings in existing web/global settings shapes; secrets stay env/profile with masking consistent with current settings API.
- Add focused tests for unauthorized access denied, valid token accepted, and localhost compatibility behavior.

## Keep
- Do not build a full custom user-account/password IdP inside Onion.
- Do not weaken MCP auth (`T-261005-01`); prefer shared helpers over duplicated JWT logic when oauth is used for control.
- Do not bind control/MCP to `0.0.0.0` in this ticket; auth is for when a tunnel/VPN makes localhost reachable.
- Do not expose raw API keys, tunnel tokens, or access tokens in UI/logs.

## Done
- Unauthenticated requests to protected control API routes fail closed.
- Authenticated client (UI or curl) can use the dashboard flows that exist today.
- Local-only compatibility mode still works when intentionally configured.
- Tests cover deny/allow paths for control auth.
