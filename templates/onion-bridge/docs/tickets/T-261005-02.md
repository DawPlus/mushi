# T-261005-02 — Migrate backend to NestJS + TypeScript

## Goal
Move the Onion Bridge backend (CLI, MCP bridge, web control API) from plain Express/JS onto a thin NestJS + TypeScript foundation so later auth and features have clear module boundaries, without changing product behavior in this ticket.

## Do
- Introduce a TypeScript + NestJS build for backend code (Nest app bootstrap, `tsconfig`, build/start scripts) while keeping the public CLI entry `onion` / `bin/onionBridge.js` working.
- Migrate existing backend surface into Nest modules with minimal behavior change:
  - MCP bridge (`/health`, `/mcp`, tunnel spawn, profile/workspace boot)
  - Web control API (`src/control/*` routes and managers)
  - Shared setup/config/workspace helpers as Nest-friendly providers or plain TS modules imported by Nest
- Preserve CLI commands and runtime contracts: `onion`, `onion start <profile>`, `onion web` / control port, localhost binding, settings/profile paths, concurrent-bridge rules.
- Port focused backend tests (`test/**`) to the new layout and keep them green; add only the minimum Nest bootstrap smoke needed for acceptance.
- Update Code Map entry points after the move.
- Leave `apps/web` as-is (already React + TypeScript + Tailwind).

## Keep
- Do not implement OAuth/JWT resource-server work here; that remains `T-261005-01` after this lands.
- Do not add DB, Passport Authorization Server, users/tenants, or unrelated refactors.
- Do not change MCP tool allowlists, tunnel-client integration, or web UI behavior except as required by import paths.
- Prefer a thin Nest shape (modules + providers + existing Express-style handlers adapted) over a large “enterprise” stack (TypeORM, CQRS, full Passport suite).
- Prefer `jose` (or equivalent) later for OAuth; do not lock the migration into `@nestjs/jwt` assumptions.
- Do not commit or publish unless explicitly asked.

## Done
- Backend builds and runs via Nest+TS toolchain.
- `onion` / `onion start` / `onion web` still start and expose the same local endpoints in intent (MCP + control).
- Existing focused backend tests pass under the new layout (or clearly replaced equivalents).
- Module boundaries exist at least for MCP bridge, control API, and shared config/setup.
- `docs/CODE_MAP.md` points at the new entries.
- No OAuth behavior change required beyond keeping current static bearer / local auth working as today.
